# Wardrobe Business

Закрытое приложение для учёта закупок, партий, продаж и прибыли магазина одежды.
Интерфейс перенесён из проекта Figma Make «Wardrobe Business Dashboard» без редизайна.
Демонстрационные данные заменены данными сервера.

```
wardrobe-business/
├─ client/              Frontend — Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4,
│                       Apollo Client 4, Zustand, React Hook Form, Recharts, Lucide React, Framer Motion
├─ server/              Backend — NestJS 12 (Express), GraphQL (Apollo, code-first), Prisma 7, PostgreSQL,
│                       class-validator, JWT + Passport + bcrypt, ConfigModule, Throttler
├─ docker/              инициализация PostgreSQL (база для тестов)
├─ docker-compose.yml   PostgreSQL 17 для разработки
└─ package.json         npm workspaces и общие команды
```

## Требования

- Node.js **20.19+** (рекомендуется 22 LTS) и npm 10+.
- PostgreSQL 14+. Проще всего запустить его через Docker Desktop: `docker compose up -d`.

## Установка и запуск

Команды для Windows PowerShell. Для macOS/Linux см. раздел ниже.

```powershell
cd $HOME\Desktop\wardrobe-business

# 1. Зависимости обоих приложений (npm workspaces, один package-lock.json).
#    При установке автоматически генерируется Prisma Client.
npm install

# 2. PostgreSQL на localhost:5432 (база wardrobe и база wardrobe_test для тестов)
npm run db:up

# 3. Переменные окружения
Copy-Item server\.env.example server\.env
Copy-Item client\.env.example client\.env.local
#    В server\.env обязательно задайте JWT_ACCESS_SECRET — случайную строку из 32+ символов:
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"

# 4. Таблицы базы данных (миграции Prisma)
npm run db:migrate

# 5. Два аккаунта, категории и курсы валют (идемпотентный seed)
npm run db:seed

# 6. Запуск API (http://localhost:4000/graphql) и сайта (http://localhost:3000)
npm run dev
```

После запуска откройте <http://localhost:3000> и войдите одним из двух аккаунтов.

### Seed: два аккаунта

`npm run db:seed` создаёт ровно два аккаунта со стабильными идентификаторами (слот 1 и слот 2).
Если аккаунта ещё нет, seed запросит в терминале его email, пароль (ввод скрыт), имя и фамилию.
Пароль нигде не сохраняется: в базе хранится только bcrypt-хеш.

Повторный запуск seed безопасен. Существующие аккаунты остаются без изменений, даже если владелец уже сменил email или пароль.

Начальные данные можно передать и через переменные окружения: `SEED_USER1_EMAIL`, `SEED_USER1_PASSWORD`,
`SEED_USER1_FIRST_NAME`, `SEED_USER1_LAST_NAME` и аналогичные `SEED_USER2_*`. Так удобно в CI. Реальные пароли не храните в
файлах, которые попадают в Git. Email сохраняется в нижнем регистре, другие исправления к нему не применяются.

### macOS / Linux


### Без Docker

Создайте пользователя и базу в своём PostgreSQL и укажите адрес в `DATABASE_URL` в файле `server/.env`, например
`postgresql://user:password@localhost:5432/wardrobe?schema=public`. Затем выполните шаги 4–6.

## Переменные окружения

Полный список с комментариями — в файлах `server/.env.example` и `client/.env.example`. Главные переменные:

| Переменная | Где | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | server | подключение к PostgreSQL |
| `JWT_ACCESS_SECRET` | server | секрет access-токенов (32+ символа) |
| `CLIENT_ORIGIN` | server | адрес сайта (CORS и cookie), по умолчанию `http://localhost:3000` |
| `COOKIE_SECURE` | server | `true`, если сайт работает по HTTPS |
| `STORE_GRAPHQL_URL`, `STORE_LOGIN`, `STORE_PASSWORD` | server | синхронизация с магазином (см. ниже) |
| `STORE_SYNC_INTERVAL_MINUTES` | server | автосинхронизация; `0` — только кнопкой в «Настройках» |
| `API_URL` | client | адрес NestJS API для прокси Next.js, по умолчанию `http://localhost:4000` |

Браузер обращается только к сайту Next.js. Запросы `/graphql` и `/uploads` проксируются в API, поэтому
refresh-cookie остаётся first-party. Служебные секреты магазина в браузер не передаются.

## Авторизация и безопасность

- Регистрации, приглашений и API для создания пользователей нет. Таблица `users` на уровне БД допускает только слоты 1 и 2 (`CHECK slot IN (1,2)`).
- Вход возвращает короткоживущий access JWT (15 минут). Он хранится только в памяти браузера.
  Refresh-токен хранится в **HttpOnly** cookie (`SameSite=Lax`, путь `/graphql`). В базе лежит только его SHA-256.
- Refresh-токены ротируются при каждом обновлении. Повторное использование старого токена отзывает всю цепочку сессий.
  Исключение — короткое окно `REFRESH_REUSE_GRACE_SECONDS` для параллельных вкладок.
- Выход отзывает сессию. В профиле видны активные сеансы, каждый можно завершить.
- Смена email и пароля требует текущий пароль. Новый email должен быть уникальным.
  Смена пароля отзывает все сессии, а текущий браузер получает новую.
- Удаление партий и товаров подтверждается паролем аккаунта. Пароль проверяет сервер.
- Все GraphQL-операции и загрузка файлов, кроме входа и обновления сессии, закрыты глобальным guard на сервере.
- Попытки входа ограничены (`LOGIN_RATE_LIMIT`, 5 в минуту), общий лимит запросов задаёт Throttler.
- Фото проверяются по сигнатуре файла (JPEG/PNG/WebP/GIF/AVIF), имена файлов — случайные UUID.

## Расчёты закупок

Товар и закупка — разные сущности. Один товар (`WR-001`) может закупаться много раз по разной цене и с разным карго.
Каждая закупочная партия (лот) хранит свою валюту и курс к UZS на момент ввода.

| Показатель | Формула |
| --- | --- |
| Стоимость закупки | закупочная цена единицы × количество |
| Карго на единицу | общая стоимость карго / количество |
| Себестоимость единицы | закупочная цена + карго на единицу |
| Цена продажи (ввод наценки) | себестоимость × (1 + наценка / 100) |
| Наценка (ввод цены или суммы наценки) | (цена продажи / себестоимость − 1) × 100 |
| Ожидаемая прибыль лота | (цена продажи − себестоимость) × количество |

Правила расчётов:

- Деньги хранятся в `DECIMAL`, расчёты выполняются через Decimal без Float.
- Округление — ROUND_HALF_UP: суммы до 2 знаков, себестоимость единицы до 4 знаков, наценка до 2 знаков.
  Итоги считаются от неокруглённых промежуточных значений.
- Окончательные значения считает сервер. Форма показывает предварительный расчёт по тем же формулам.
- Количество — целое число больше 0. Закупочная цена больше 0, карго не меньше 0.
  Количество в лоте нельзя уменьшить ниже уже проданного. Деления на ноль нет.
- **Выручка** — сумма засчитанных продаж магазина.
  **Фактическая прибыль** = выручка − себестоимость проданных единиц по FIFO из лотов товара. Она считается только для товаров, связанных с магазином.
  Проданные единицы без известной себестоимости в прибыль не попадают (`unallocatedUnits`).
  **Ожидаемая прибыль** считается по формуле выше.
- «Чистая прибыль» партии = выручка партии − все её затраты. Процент берётся от затрат партии.
- Аналитика строится по рабочим дням Ташкента (UTC+5, `BUSINESS_UTC_OFFSET_MINUTES`).
  Суммы на сервере хранятся в UZS. Интерфейс показывает их в выбранной валюте по общим курсам со страницы «Конвертация».

Удаление не уничтожает финансовую историю:

- Лот с продажами переносится в архив.
- Лот без продаж удаляется.
- Партия с лотами архивируется, а её товары остаются в списке без партии.

## Синхронизация с магазином (style-hub-back)

Синхронизация выполняется только сервером. Браузер и база магазина напрямую не связаны.

- **Настройка.** В `server/.env` укажите `STORE_GRAPHQL_URL` (GraphQL API магазина), `STORE_LOGIN` и `STORE_PASSWORD`.
  Это учётная запись магазина с ролью `ADMIN`. Запуск — кнопкой «Синхронизировать» в «Настройках» или по расписанию (`STORE_SYNC_INTERVAL_MINUTES`).
- **Что читается.** Операции `login`, `productsAdmin` (id, sku, остаток, `soldCount`) и `allOrders` (позиции заказов) читаются постранично.
- **Сопоставление.** Товар связывается с товаром магазина по стабильному внешнему идентификатору — `sku` или `id` товара магазина.
  Их указывают в поле «ID / SKU товара на wardrobestore.uz». Сопоставления по названию нет.
- **Что считается продажей.** Позиция заказа засчитывается, если у заказа `paymentStatus = PAID` и `status ≠ CANCELLED`.
  Если оплаченный заказ потом отменили, продажа при следующей синхронизации перестаёт учитываться.
- **Безопасный повтор.** Записи обновляются по внешним ID заказа и позиции, поэтому повтор не дублирует продажи.
  Синхронизация ничего не списывает ни в одной системе.
- **Остатки.** Источник истины для остатков — поле `stock` магазина. Оно показывается в карточке товара.
  Остаток лота в таблицах — это закупленное количество минус продажи, распределённые по FIFO.
- Каждый запуск журналируется: время, число заказов, новые и обновлённые продажи, ошибка.

### Чего не хватает в API style-hub-back

Чтобы учёт был полным, в style-hub-back нужно добавить:

1. **Возвраты.** Сейчас в заказах нет статуса `RETURNED` и записи о возврате позиции. Возврат после оплаты отличается от продажи только отменой всего заказа.
   Нужен статус или модель возврата по позициям с датой.
2. **Складские списания.** Списания `StockDeduction` («ombor», Telegram) недоступны через GraphQL.
   Нужен admin-запрос, например `stockDeductions(filter: { updatedAfter, page, limit })`, чтобы учитывать списания отдельно от продаж.
3. **Инкрементальная синхронизация.** У `allOrders` и `productsAdmin` нет фильтра `updatedAfter`, поэтому сейчас при каждом запуске читаются все страницы.
   При большом числе заказов нужен фильтр по `updatedAt`.
4. **Сервисный доступ.** Вместо пароля администратора лучше выделить отдельную учётную запись или API-ключ только для чтения.
5. **Варианты.** Продажи сопоставляются на уровне товара. Если нужен учёт по вариантам (`ProductVariant`: размер и цвет), в `OrderItem` нужен стабильный `variantId`.

## Тесты и проверки

`npm test` запускает тесты:

- **Backend.** Тесты Vitest лежат в `server/test`. Для них нужна база PostgreSQL:
  укажите `TEST_DATABASE_URL`, например `postgresql://wardrobe:wardrobe@localhost:5432/wardrobe_test` из docker compose.
  Без этой переменной тесты сами поднимут временный PostgreSQL (пакет `embedded-postgres`).
  - Авторизация: вход обоими аккаунтами, неверный пароль, запрет без токена, невозможность создать третьего пользователя.
  - Сессии: ротация, повторное использование токена, выход, смена email и пароля с отзывом сессий, идемпотентный seed.
  - Расчёты: формулы, округление, валидация.
  - Закупки и партии: архивирование, сохранение данных после перезапуска.
  - Синхронизация с тестовым двойником API магазина: статусы, отмены, отсутствие дублей, привязка по ID/SKU.
  - Загрузка фото.
- **Frontend.** `client/src/lib/utils/pricing.test.ts` проверяет, что предварительный расчёт формы совпадает с серверным.

## Продакшн

- Задайте `NODE_ENV=production`, надёжный `JWT_ACCESS_SECRET`, `COOKIE_SECURE=true` и реальный `CLIENT_ORIGIN`.
- Выполните `npm run build` и `npm run db:migrate`, затем `npm start`. Можно запускать приложения отдельно под process manager.
- Папку загрузок (`UPLOAD_DIR`) храните на постоянном диске и включите в резервные копии вместе с базой.
- Регулярно делайте резервные копии PostgreSQL (`pg_dump`).
